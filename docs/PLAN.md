# Listora — Implementation Plan

> **Status (3 Oct 2026):** Phases 0–6 implemented, except login (deferred by decision — no auth in v1). Library lists all listings. Runs fully in mock mode; real AI/Neon/Blob/Upstash need credentials in env.

Upload one normal product photo → get 1–3 marketplace-ready images + every Meesho listing field, ready to copy.

---

## 1. Scope (v1)

**The user does only two things on the UI:**
1. Upload a product photo
2. Pick how many images they want: **1, 2 or 3**

Everything else (category, pack size, material, measurements, title, description…) is inferred by AI and shown as editable fields. Anything the AI guessed is marked **"Estimated — please verify"**. Price and stock are not generated — Meesho sets those in the seller panel (as in the design).

**Out of v1:** other marketplaces, analytics page ("Coming later" in design), payments, team accounts.

## 2. Tech stack

| Layer | Choice | Notes |
|---|---|---|
| Framework | **Next.js (App Router) + TypeScript** | UI + API routes in one project |
| Styling | **Tailwind CSS + shadcn/ui** | Port the Listora design (Archivo font) |
| Validation | **Zod** | One schema shared by API, AI output and forms |
| Text AI | **OpenAI — latest GPT (GPT-6 family) with Structured Outputs** | Reads the photo, returns listing JSON |
| Image AI | **OpenAI `gpt-image-2.5` (flare)** + **Gemini `gemini-3.1-flash-image` (Nano Banana 2)** | Both used for every image — see §5 |
| Database | **Neon Postgres** (via Vercel Marketplace) + **Drizzle ORM** | Replaces Supabase. One-click on Vercel, free tier, DB branch per preview deploy |
| File storage | **Vercel Blob** | Original photo + generated images |
| Auth | _Deferred_ — no login in v1. Later: **Better Auth** (Google + magic link) | Rate limit per IP until then |
| Rate limit | **Upstash Redis** (via Vercel Marketplace) | Stops one user burning the AI budget |
| Image processing | **sharp** | Resize, make square, white padding, JPEG export |
| ZIP export | **JSZip** (in browser) | "Download all" |
| Hosting | **Vercel** | Preview deploy per PR, prod on `main` |
| Tests | **Vitest** (logic) + **Playwright** (one end-to-end smoke test) | |

> **Model IDs change often.** All model names live in env vars (§9) so we can switch without code changes. Verify the exact IDs on day 1 of Phase 2/3.

**Why not Supabase:** Neon + Vercel Blob + Better Auth gives the same three things (DB, files, login), all billed and managed inside Vercel, and nothing is tied to one vendor's SDK — Drizzle works with any Postgres.

## 3. User flow

```
[Upload photo] → [Pick 1 / 2 / 3 images] → [Generate]
        │
        ▼
Step 1  GPT analyses photo  ──►  listing details shown (~5–10 s)
        + writes a "shot plan" (one prompt per image)
        │
        ▼
Step 2  For each image slot, OpenAI and Gemini run in parallel
        → 2 candidates per slot appear as they finish (~15–40 s)
        → user taps the better one (or "Regenerate")
        │
        ▼
Step 3  Copy fields one by one  /  Download ZIP (selected images + listing.txt)
```

Image slots, in order (count decides how many are used):

| Count | Slots |
|---|---|
| 1 | Primary |
| 2 | Primary, Angle/Detail |
| 3 | Primary, Angle/Detail, Size/Features |

- **Primary** — product alone, pure white background, no text, no props.
- **Angle/Detail** — different angle or close-up of texture/finish.
- **Size/Features** — one product with measurement arrows or 2–3 short callouts; measurements labelled "approx." if estimated.

Every image is a **separate file** — never a collage (rule from the skill).

## 4. Architecture

```
Browser (Next.js page)
  │ 1. compress photo (≤2048px JPEG) → upload straight to Vercel Blob
  │ 2. POST /api/listings            { sourceUrl, imageCount }
  │      → GPT analysis → save listing → return details + shotPlan
  │ 3. for each slot × provider, in parallel:
  │    POST /api/listings/:id/images { slot, provider }
  │      → image model → sharp → Vercel Blob → save row → return URL
  │ 4. PATCH /api/listings/:id        (user edits fields / picks image)
  ▼
Neon Postgres  ◄── Drizzle      Vercel Blob  ◄── images
```

**Why one request per image (not one big request):**
- Each call stays well under Vercel's 300 s function limit (Hobby).
- Images appear one by one instead of all at the end.
- "Regenerate" is the same endpoint — no extra code.
- If Gemini fails, the OpenAI candidate still shows (and vice versa).

**Vercel 4.5 MB body limit:** never send image bytes through our API. Photo goes browser → Blob directly (Blob client upload); generated images go server → Blob and only the URL comes back.

## 5. Using both image models

Default mode **`dual`**: every slot is generated by **both** OpenAI and Gemini at the same time. The user sees two options per slot and picks one.

| Mode (env `IMAGE_MODE`) | What happens | Cost per 3-image listing |
|---|---|---|
| `dual` (default) | Both providers per slot, user picks | 6 image calls |
| `fallback` | Gemini first, OpenAI only if Gemini fails | 3 image calls |

Both providers get the **same input**: the original photo as a reference image + the slot prompt from the shot plan + fixed rules:

> Keep the exact same product — do not change color, shape, logo, texture or proportions. One product presentation per image. No collage, no grid, no watermark.

Provider code sits behind one interface so adding a third model later is one file:

```ts
interface ImageProvider {
  name: 'openai' | 'gemini';
  generate(input: { referenceImage: Buffer; prompt: string; size: '1024x1024' }): Promise<Buffer>;
}
```

After generation, `sharp` normalises every image: square, white padding, JPEG, ~1500×1500.

## 6. AI listing output (GPT)

The skill file (`MEESHO_PRODUCT_LISTING_SKILL.md`) becomes the **system prompt**, adapted for "no questions — mark assumptions instead". GPT must return this Zod schema (Structured Outputs = guaranteed valid JSON):

```ts
const Field = z.object({
  key: z.string(),            // "product_name", "material", ...
  label: z.string(),          // "Product Name"
  value: z.string(),          // short, copy-paste ready
  note: z.string().nullable(),
  source: z.enum(['visible', 'estimated', 'unknown']),
  verify: z.boolean(),        // show "please verify" badge
});

const Listing = z.object({
  summary: z.object({ product: z.string(), category: z.string(), intendedUse: z.string(),
                      packQuantity: z.number(), color: z.string(), material: z.string(), brand: z.string() }),
  fields: z.array(Field),                 // Meesho fields, only those that apply
  measurements: z.array(z.object({ name: z.string(), cm: z.number().nullable(),
                                   inch: z.number().nullable(), approximate: z.boolean() })),
  title: z.string(), altTitles: z.array(z.string()).max(2),
  description: z.string().max(1400),
  keywords: z.array(z.string()).min(5).max(10),
  shotPlan: z.array(z.object({ slot: z.enum(['primary', 'detail', 'size']), prompt: z.string() })),
  verifyBeforePublishing: z.array(z.string()), // weight, HSN/GST, manufacturer, origin, MRP
  assumptions: z.array(z.string()),            // e.g. "Assumed pack of 1"
});
```

Hard rules enforced in the prompt **and** in code after the response:
- HSN / GST / manufacturer / packer / importer / country of origin → never invented; `source: 'unknown'`, `verify: true` unless clearly visible.
- Title pack quantity must match `summary.packQuantity` (code check).
- Weight is always `verify: true`.

## 7. Database (Drizzle schema)

```
user, session, account, verification   ← created by Better Auth

listing
  id            uuid pk
  user_id       fk → user
  source_url    text            -- original photo in Blob
  image_count   int  (1–3)
  status        enum(analysing, ready, failed)
  details       jsonb           -- Listing JSON (user edits saved here)
  text_model    text
  created_at, updated_at

listing_image
  id            uuid pk
  listing_id    fk → listing (cascade)
  slot          enum(primary, detail, size)
  provider      enum(openai, gemini)
  model         text
  prompt        text
  url           text null
  status        enum(pending, done, failed)
  error         text null
  selected      bool default false
  created_at

usage_event                       -- cost tracking
  id, user_id, listing_id, provider, model, kind(text|image), cost_usd, created_at
```

## 11. Risks and how we handle them

| Risk | Handling |
|---|---|
| AI changes the product (color/shape) | Reference photo sent to both models + strict prompt; dual mode lets user pick the faithful one; Regenerate |
| AI invents specs (HSN, weight, maker) | Schema forces `source` + `verify`; code overrides compliance fields to "unknown" |
| Slow image calls | Parallel per-slot requests, progressive UI, 120 s cap per call |
| Cost runaway | Rate limit + daily cap + `usage_event` tracking + `fallback` mode switch |
| Model renamed / retired | Model IDs in env vars, provider interface |
| Large uploads | Client compression + direct-to-Blob upload |
| Meesho image rules change | Slot rules kept in one file (`slots.ts`) |
